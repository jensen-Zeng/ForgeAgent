# 失败案例与经验

## 1. Python 字节码缓存导致“已修复但测试仍失败”

在同一秒内把 Python 文件改成相同字节数时，时间戳式 `.pyc` 可能仍被复用。补丁工具现在会在成功修改 Python 文件后清理对应缓存；这也说明 Agent 必须把测试输出当作观察，而不是盲信写入成功。

## 2. Provider 工具参数并不总是规范 JSON

OpenAI-compatible 服务可能返回截断 JSON、数组或缺失 `arguments`，Anthropic 又使用不同的内容块协议。适配层统一规范化并拒绝含糊参数，回归测试覆盖文本、工具调用、用量、重试和错误；但具体代理服务仍需真实烟雾测试。

## 3. 安全命令仍会执行仓库代码

`pytest` 被策略归类为 SAFE，只表示命令形状符合窄白名单，并不表示目标代码可信。默认 `auto` 路由为了速度仍在本地运行 SAFE 命令；环境变量会被净化，命令有超时与输出上限，但真正的网络和资源硬边界仍依赖经过宿主验证的容器。处理不可信仓库时应显式选择 `docker` 全量后端。

## 4. Docker 宿主条件不足

在没有可用 Docker daemon 或目标镜像的环境中，只能验证最小权限规格、路由和错误处理，不能据此声称完成了真实隔离。镜像构建、敏感宿主文件不可达和资源限制必须在实际部署的宿主上验收。

自动路由采用失败关闭：需要 Docker 的命令在运行时不可用时返回 `sandbox_unavailable`，不会回到本地。这个设计避免静默失去隔离，但也意味着安装 Docker 和构建目标镜像之前，格式化、包管理等 `REVIEW` 命令无法在默认模式下完成。

## 5. 费用数据可能不完整

部分 Provider 只返回 Token，不返回美元费用。本地 `max_cost` 只能累计已知费用，并在响应返回后停止；真实测试必须使用服务商控制台硬限额，不能把本地预算当作计费保险。

## 6. RLM 的可信 Kernel 不是沙箱

持久 IPython 允许模型直接导入 `os`、`subprocess` 或文件 API。Host Bridge 的严格参数、密钥环境净化和 `--trust-workspace` 拒绝门禁能降低误用与泄漏风险，但无法把任意 Python 变成受限工具。默认 `forge run` 不启动 Kernel；RLM 只用于用户已经审查并愿意以当前账户权限执行的仓库。

## 7. 崩溃恢复不能猜测副作用

如果进程在工具、child 或 Kernel 操作执行期间退出，JSONL 可能只有开始事件而没有可靠终态。自动重放可能重复写文件、安装包或调用外部服务，因此恢复逻辑把这类操作标为 `interrupted/uncertain`，只继续从未开始的持久输入。半写 JSONL 尾行也只报告 `last_good_offset`，必须由用户显式执行 `forge session repair ... --truncate-tail`。
